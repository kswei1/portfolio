Redesigning Block Builder's workspace for a growing platform

A new workspace structure that helps 50+ teams find capabilities, navigate complex page hierarchies, and work with less friction.

TeamContent Platform
RoleProduct Designer II
TimelineAug 2025 – Jan 2026
StakeholdersPM, EM and Engineers

Overview

What is Block Builder

Block Builder is Wayfair's internal CMS — the platform 50+ cross-functional teams use to build, configure, and publish everything customers see on Wayfair.com. Think Squarespace or Webflow, but far more complex: PMs, marketing, analysts, engineers, and designers all create, target, and experiment with content here.

The problem

The platform grew, but the workspace didn't

As different teams needed different capabilities, Block Builder grew more complex. But everyone kept working in essentially the same workspace — and it never evolved with the platform. Two problems kept surfacing:

Problem A

Finding capabilities was harder than it should be

Targeting, experimentation, block groups, and other features all lived in one long list. Different roles needed different capabilities to complete their jobs, but everyone had to navigate the same list to find what they needed.

Users had to scroll through the list to find the right tool.

Problem B

Users had to go through too many layers to reach what they needed

Blocks could be nested many levels deep. To reach a block buried ten levels down, users had to click through nine drawers — then close them one by one to get back.

Why it mattered

Block Builder is internal, but it directly powers Wayfair.com. Teams build and publish pages — often for time-sensitive promotions and seasonal campaigns — and QA every block before it goes live. When finding features and navigating pages is hard, teams spend more time building, editing, and checking content, and every new capability makes the workspace harder still.

The reframe

The problem wasn't just navigation

My first idea wasn't the answer. I explored an "overview" concept — like the relationship between a Google Drive folder and a Google Doc: a high-level view of a page and its contents, with breadcrumbs to show where you were, then drill into individual blocks.

But talking it through with stakeholders, it created another problem. An overview for every page added a layer of its own and likely needed backend and data changes — and even with breadcrumbs, reaching deeply nested content could still take many steps. It treated the symptom, not the cause.

That was the turning point. I stepped back and looked at how other complex products structure dense workflows, and reframed the challenge — from making navigation easier to restructuring the workspace and its interaction model.

How might we restructure the workspace so users can easily access the capabilities they need, navigate complex page structures, and keep working — without adding more complexity to the platform?

How I drove the direction

Finding what we could safely change

I drove the direction from framing the problem through MVP and Post-MVP. Because Block Builder powers the live site, large backend changes carried real production and business risk — a full rebuild wasn't realistic. So a core constraint became: improve the experience primarily through UI and frontend changes while preserving the existing backend.

UI + frontend change while preserving existing backend behavior

I brought engineering into the design early instead of designing first and handing off. Together we worked out what was frontend-only, what needed backend work, which existing components we could reuse, and what belonged in MVP versus Post-MVP — so we could ship real improvements without adding platform risk.

User feedback → Exploration → Prototype → PM / Eng feasibility → Iteration → MVP / Post-MVP

Competitive research

Studied complex products — Contentful, Sanity, Figma — to see how they organize capabilities and dense workflows.

Prototypes to align

The solution

A workspace built around how people work

Instead of treating navigation as a separate layer, I restructured the workspace into three parts that work together — so capabilities, editing, and preview each have a clear place instead of competing for the same space.

Why this structure

I wasn't trying to make a three-panel UI

Three panels weren't the goal — a workspace that fit how people actually work was. Four inputs pointed to this structure:

User needs

Easier access to capabilities and better navigation through deep page hierarchies.

Current workflow

Capabilities, editing, and preview all need to coexist so users can build and validate the result.

Competitive research

Panel-based workspaces are common in complex products — dense functionality without one crowded layer.

Future direction

Room for new capabilities like Blocky / AI without another major workspace redesign.

Design trade-off

When I couldn't change the component, I changed the interaction

The Drawer was deeply tied to the platform architecture, so replacing it wasn't safe. But stacked drawers were a real usability problem — move between capabilities and each one stacked another layer, until users were five deep and had to close five to get back. So I changed the interaction model: one drawer that switches content in place, with lighter visual treatment so it no longer felt like layers piling up.

Deep dive

Menu navigation

I reimagined and reused the existing feature as a menu-based navigation — simplifying navigation without backend changes, saving the engineering time to build from 0 to 1, and removing the need to open multiple drawers. Through iteration, I refined how information is displayed.

  • The initial version (V1) only showed block titles, which made it hard to tell similar blocks apart.
  • In the final version, I used the block title as the primary label and added block type and ID as secondary information in a lighter, smaller style.

The result is a more intuitive navigation experience: users understand the structure, identify blocks quickly, and move through nested content without losing context.

A flexible system

Flexible panel architecture (3 panels + AI agent)

As a complex platform, the design needed to support multiple panel configurations — not just a fixed 3-panel layout. In addition to navigation, editing, and preview, we also introduced an AI agent (Blocky) as an optional panel. Since we envision AI-assisted workflows as a core part of the platform's future, it was important to ensure users can always access it.

Reflections

Building in the unknown

This project had a lot of ambiguity. I identified the problem and led it end-to-end without a clear roadmap. Through user insights, research, and close collaboration with stakeholders, I defined the MVP and Post-MVP approach, aligned priorities, and drove it to launch.

Designing within constraints

At the same time, I had to design within tight constraints on a complex, high-risk platform. I worked closely with engineering to find feasible solutions, reusing existing systems where possible — and balanced different user needs so it stayed easy for new users while still powerful for advanced ones.
